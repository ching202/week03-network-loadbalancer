Objective & Overview
In modern cloud and enterprise systems, applications are never deployed to flat, unprotected networks. Application architects design isolated network segments (public ingress vs. private application tiers) and use load balancers to distribute traffic, terminate TLS, and prevent single-point-of-failure bottlenecks.

When developers use AI to generate infrastructure configurations (e.g., Docker Compose networks, Terraform, Nginx configs, or cloud VPC templates), LLMs often take dangerous shortcuts—such as binding private backend containers directly to host ports, hallucinating non-existent upstream directives, or creating flat networks where every service can touch the public internet.

In this assignment, you will:

Use an AI tool to generate an initial draft of a multi-subnet network topology with a functional load balancer (e.g., Nginx, HAProxy, Envoy, or cloud ALB/Traefik) distributing traffic across multiple backend web application instances.
Audit and verify the AI-generated network definitions to enforce subnet isolation (public vs. private tiers) and verify load distribution algorithms (Round-Robin, Least Connections).
Execute a structured Web Project QA test suite to verify traffic balancing, zero-downtime failover, and network segmentation.
Deploy and submit your project with a GitHub repository, AI prompt log, live URL (if applicable), and a video walkthrough demonstrating functionality, failover, and networking tests.
Step-by-Step Instructions
Step 1: Prompt the AI for an Initial Draft
Students can implement this using Docker Compose with custom bridge networks (accessible on any local machine) or using Infrastructure as Code / Cloud VPCs (AWS/GCP/Azure with Terraform).

Sample Initial Prompt for Students to Copy & Adapt:

Act as a senior network systems architect. I need a multi-container network topology configured using Docker Compose (or Terraform/Cloud IaC) demonstrating isolated subnets and reverse-proxy load balancing for a web application.

 

The architecture must include:

Two Isolated Network Subnets:
   - 'public_subnet': Accessible from the host/internet.

   - 'private_subnet': Isolated backend network with no direct external port exposure.

A Load Balancer (Nginx or HAProxy):
   - Dual-homed on both 'public_subnet' and 'private_subnet'.

   - Exposes port 80/443 to the host.

   - Configured with an upstream pool distributing requests across backend instances using Round-Robin.

At least Two Web Application Backend Replicas (e.g., Node.js, Python, or Go):
   - Connected ONLY to 'private_subnet'.

   - Each instance must return a unique identifier (e.g., container hostname or server ID) so I can verify which instance handled the request.

   - Includes a simple health-check endpoint (/healthz).

 

Provide the Docker Compose file, the load balancer configuration file (e.g., nginx.conf), the minimal backend application code, and step-by-step instructions to run and test it.

 

Step 2: Audit & Verify the AI Output (Networking & Security Checklist)
Before running the generated infrastructure, review what the AI produced against this Network Reality Check:

Port Leakage & Network Isolation: Did the AI map the backend instances' ports to the host machine (e.g., ports: ["3001:3000"])?
Correction: Backend containers must never expose ports directly to the host. They must use expose: or internal container ports visible only within the private_subnet.
Subnet Dual-Homing: Is the load balancer the only service connected to both the public and private subnets? The backend apps must not have an interface on the public network.
Upstream Configuration & DNS Resolution: Did the AI hardcode static container IPs, or did it use internal Docker/cloud service discovery names? Did it include connection timeouts and retry buffers (proxy_next_upstream in Nginx)?
Session Persistence vs. True Balancing: Verify whether the AI generated a round-robin, least-connections, or IP-hash algorithm, and ensure it correctly balances stateless requests across all backends.
Step 3: Web Project Testing & Quality Assurance (QA) Checklist
Run your infrastructure through this QA framework. You will demonstrate these live in your recording:

[ ] 1. Load Distribution Verification (Round-Robin Test):
Send at least 10 consecutive requests (via browser refresh, curl, or Postman).
Confirm that responses alternate evenly between Backend Instance 1 and Backend Instance 2 based on the returned container hostname/ID.
[ ] 2. High Availability & Failover Test:
Stop or kill one backend instance (e.g., docker stop backend_1).
Issue requests to the load balancer: confirm that 100% of requests are transparently routed to the remaining healthy instance with zero dropped requests (502 Bad Gateway avoided).
Restart the stopped instance and verify it automatically re-enters the active balancing pool.
[ ] 3. Network Boundary & Isolation Test (Negative Test):
Verify from the host machine that direct HTTP connections to internal backend container ports (e.g., curl http://localhost:3001) are rejected or unreachable.
Prove that the backend can only be reached through the reverse-proxy load balancer on the public gateway.
[ ] 4. Browser Console & Health Check Status:
Load balancer health-check endpoint returns HTTP 200 OK.
Browser DevTools Network tab shows proper HTTP status codes, headers, and clean connection reuse.
Console is clean with zero client-side or gateway routing errors.
